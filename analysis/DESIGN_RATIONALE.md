# 설계 근거 문서 (Design / Motivation 초안)

이 문서는 viewport prediction 파이프라인이 `baseline`(단일 CLS 토큰) →
`all-patch`(전체 패치) → `patch-selection`(선택된 패치) → 온라인 ViT로 이어지는
현재 형태에 도달한 **논리적 이유**를 정리한다. 시간순이 아니라 "왜 이전 설계가
불충분했고, 다음 설계가 그 불충분함을 어떻게 해소했는가"의 인과 사슬로 구성했다.
각 절은 (1) 문제, (2) 채택한 해법과 그 이유, (3) 당시 고려했던 대안과 기각 이유
순으로 적는다. 이 문서는 논문 Design/Motivation 섹션의 초안으로 쓰기 위한 것이다.

**용어 구분 (중요)**: 이 프로젝트에는 "baseline"이라는 말이 두 가지 다른 대상을
가리키는 데 쓰여 혼동하기 쉽다. 이 문서를 포함한 모든 patch-selection 관련
문서에서 **"baseline"은 항상 아래 §1에서 설명하는 단일 CLS 토큰 멀티모달 모드**를
가리킨다. 궤적 정보만 쓰고 이미지를 전혀 쓰지 않는, LR(회귀)/Velocity와 비교되던
NetLLM 원본 설정은 **"text-only"**로 구분해서 부른다 — text-only는 이 문서의
논의 대상이 아니다(text-only vs LR/Velocity MAE 비교는 이미 별도로 확인되어 있다).

| 용어 | 의미 | 비교 대상 |
|---|---|---|
| text-only | 멀티모달 없음, 궤적만 사용 | LR(회귀) / Velocity |
| baseline | 단일 CLS 토큰 멀티모달 (§1) | all-patch / patch-selection |

## 1. Baseline이 공간 정보를 잃는 이유

### 문제

`baseline` 모드(`Pipeline._get_multimodal_information_baseline()`,
`models/pipeline.py:262-288`)는 프레임 하나당 미리 offline으로 추출해 둔 ViT
**CLS 토큰 feature 1개**(768차원)를 `embed_multimodal`로 사영해 LLM 시퀀스 앞에
토큰 1개로 붙인다.

이 feature가 어떻게 만들어지는지 보면 문제가 분명해진다
(`dataset/extract_features.py:13-38`, `extract_vit_features()`):

```python
x = model._process_input(img)                      # 224x224 이미지 -> 16x16=196개 패치 토큰
batch_class_token = model.class_token.expand(n,-1,-1)
x = torch.cat([batch_class_token, x], dim=1)        # CLS 토큰 + 196개 패치 토큰
x = encoder(x)                                       # self-attention으로 197개 토큰이 서로 정보 교환
x = x[:, 0]                                          # <- 마지막에 CLS 토큰 하나만 남기고 196개 패치 토큰은 버림
return x
```

즉 ViT 인코더 내부에서는 프레임 전체가 196개 패치 단위로 처리되고 각 패치가
self-attention을 통해 서로 정보를 주고받지만, **최종적으로 남기는 것은 CLS
토큰 하나뿐**이다. CLS 토큰은 "이 프레임에 대체로 뭐가 있는가"를 요약하도록
학습된 전역 표현이지, "프레임의 어느 위치에 무엇이 있는가"라는 공간적 질문에
답하도록 최적화된 표현이 아니다. viewport prediction은 본질적으로 "다음에 어느
**방향**을 볼 것인가"를 묻는 문제이므로, 프레임 내 위치 정보가 없는 CLS 토큰
하나로는 "시청자가 왼쪽에 있는 물체 쪽으로 이동 중"과 같은 방향-내용 연관을
LLM이 학습할 수 있는 신호 자체가 입력에 존재하지 않는다.

### 당시 고려했던 대안

- **CLS 토큰의 차원/용량을 늘린다**: `embed_multimodal`의 출력 차원을 키워도
  CLS 토큰 자체가 이미 공간 축을 소실한 압축 표현이므로(196개 패치의 attention
  가중합), 사영 차원을 늘리는 것으로는 애초에 없는 정보를 복원할 수 없다. 기각.
- **saliency map 기반 접근** (`dataset/extract_saliency.py`, gradient 기반
  ResNet50 saliency, MANSY 계열 baseline에서 상속): 프레임 내 "어디가 중요한가"에
  대한 공간 정보를 별도 맵으로 제공하는 방식으로, 이 저장소에 유산으로 남아있는
  스크립트이기도 하다. 다만 이 saliency는 입력 이미지 자체의 시각적 현저성만
  반영할 뿐 **현재 파이프라인의 궤적 조건부(trajectory-conditioned) 신호와
  결합되지 않아**, "이 사용자가 지금 보고 있는 방향" 같은 사용자별 동적 정보를
  담지 못한다. 이 프로젝트에서는 채택하지 않고, 대신 패치 단위 접근으로 방향을
  틀었다.
- **결론**: 공간 정보를 실제로 살리려면 ViT가 내부적으로 이미 계산하고 있는
  패치 단위 표현 자체를 버리지 않고 꺼내 써야 한다 → §2로 이어짐.

## 2. Patch selection을 도입한 이유 (all-patch로 다 넣지 않고 "선택"하는 이유)

### 문제

§1의 결론에 따라 프레임을 그리드로 나눠 각 패치를 독립 토큰으로 LLM에 제공하는
`all-patch` 모드를 먼저 도입했다(`patch_grid` 기본 4×4=16, `crop_patches()`,
`models/patch_selection.py:93-106`). 이는 공간 정보 소실 문제는 해결하지만, 새로운
비용을 만든다:

- **시퀀스 길이 증가**: 프레임당 토큰이 1개(CLS) → 16개로 늘어난다.
  `auto_regressive()`의 KV 캐시 도입 이후에도(`KV_CACHE_SCOPE.md` 참고) 이
  이미지 토큰들은 **매 auto-regressive 시퀀스의 최초 1회**에는 반드시 LLM을
  통과해야 하므로, 토큰 수 증가는 곧 첫 스텝의 attention 연산량 증가로 이어진다.
- **노이즈 유입**: 16개 패치 중 상당수(예: 360도 영상의 상하 극지방)는 시청자가
  거의 보지 않는 영역이다. 이런 "관련 없는" 패치까지 전부 토큰으로 넣으면,
  LLM이 실제로 유의미한 패치(시청자 시야 근처)와 배경 잡음 패치를 구분하는 부담을
  LLM 자체의 attention에 전가하게 된다. 학습 데이터가 제한적인 상황에서는 이
  구분을 명시적으로 도와주는 편이 학습 효율과 일반화에 유리하다.

### 채택한 해법

과거 viewport 궤적을 조건으로 받아 "다음 프레임에서 볼 가능성이 높은 패치"를
사전에 골라내는 `PatchSelectionModule`(`models/patch_selection.py:24-90`)을 도입해,
16개 중 관련성 높은 부분집합(top-k 또는 threshold 기반, `select_patches()`)만
ViT와 LLM에 통과시키는 `patch-selection` 모드를 만들었다. 이는 시퀀스 길이를
줄이는 동시에(연산 비용 절감), 어떤 패치가 들어가는지 자체를 궤적 신호로
필터링해 노이즈를 통제한다.

이 모듈이 "고정된 사전지식"이 아니라 실제로 궤적에 반응해 동적으로 선택하는지는
별도로 검증했다 — `PATCH_SELECTION_VERIFICATION.md` 참고.

### 당시 고려했던 대안

- **고정 규칙 기반 선택** (예: 항상 수평선 밴드만 선택): 360도 영상 시청 패턴상
  수평선 근처가 대체로 중요하다는 사전지식과 부합하지만, 개별 사용자의 실제
  이동 궤적(예: 빠르게 위/아래로 이동 중인 경우)에 반응하지 못해 궤적-이미지
  연관을 학습할 여지 자체를 차단한다. 기각.
- **all-patch를 유지하되 LLM 쪽에서 attention sparsity/pruning으로 해결**:
  LLM 내부 attention을 성기게 만드는 방식은 어떤 패치가 애초에 중요한지에 대한
  외부 지식(궤적)을 활용하지 못하고, LLM이 그 판단을 처음부터 다시 학습해야
  한다. 또한 attention pruning은 LLM 구조 자체를 건드려야 해 모듈성이 떨어진다.
  patch selection은 LLM 앞단에서 독립적인 소형 모듈로 처리할 수 있어 구조가
  단순하고, 학습도 분리되어(pretrain 후 고정) 안정적이다. 기각.
- **결론**: "몇 개를 선택할지"와 "선택된 것을 어떻게 표현할지"는 별개의 질문이다.
  선택 자체는 정했지만, 선택된 패치들을 LLM에 넣는 방식은 또 다른 설계 선택지가
  남는다 → §3.

## 3. 선택된 patch를 pooling 없이 개별 토큰으로 넣기로 한 이유 (옵션 A vs 옵션 B)

패치 선택 이후, k개의 선택된 패치를 LLM에 어떻게 제공할지에 두 가지 옵션이
있었다.

- **옵션 A (채택)**: 선택된 k개 패치를 ViT에 각각 통과시켜 k개의 독립 토큰으로
  LLM 시퀀스에 그대로 concat한다 (`_get_multimodal_information_patch_selection()`,
  `models/pipeline.py:329-345`). Pooling 없음.
- **옵션 B (기각)**: k개 패치 feature를 평균(mean pooling) 또는 다른 방식으로
  1개(혹은 소수) 토큰으로 합쳐서 넣는다.

### 옵션 A를 택한 이유 / 옵션 B의 문제

옵션 B는 시퀀스 길이를 더 줄일 수 있다는 장점이 있지만, **§1에서 CLS 토큰을
버린 것과 본질적으로 동일한 실수를 patch 레벨에서 반복**하는 문제가 있다:

- **패치 간 상대 위치 정보의 소실**: k개 패치를 평균 내면 "선택된 패치들이
  서로 어떤 배치로 놓여 있는가"(예: 왼쪽 위 + 오른쪽 아래처럼 떨어져 있는지,
  한 덩어리로 붙어 있는지)라는 정보가 사라진다. 반면 옵션 A는 각 패치가 독립
  토큰이므로, LLM의 self-attention이 원하면 토큰 간 관계(즉 패치 간 공간적
  관계)를 그대로 학습할 수 있다 — 이게 애초에 §1에서 CLS 토큰을 버리고 패치
  단위로 간 이유였다. Pooling은 그 이유를 patch selection 단계에서 다시
  무효화하는 것과 같다.
- **선택 개수(threshold 모드에서는 가변)에 대한 정보 손실**: threshold 기반
  선택에서는 선택되는 패치 수가 샘플마다 다르다(`patch_selection_history`,
  `models/pipeline.py:97,338`). k개를 평균 내 1개로 만들면 "몇 개가, 얼마나
  강하게 선택됐는지"에 대한 정보(예: 궤적 분석에서 확인된 "이동 속도가 빠를수록
  더 많은 패치가 선택된다"는 신호, `PATCH_SELECTION_VERIFICATION.md` §3)가
  LLM에 전달되지 않는다. 옵션 A는 시퀀스 길이 자체가 k이므로 이 정보가 암묵적으로
  보존된다.
- **어떤 개별 패치가 결정적이었는지 추적 불가**: 옵션 B는 pooling 이후 어떤
  개별 패치가 예측 오차에 기여했는지 사후 분석(attention 가중치 등)으로 되짚기
  어렵다. 옵션 A는 각 패치가 독립 토큰이라 attention 시각화 등으로 patch 단위
  해석이 가능하다 (이번 검증 작업의 heatmap/케이스 스터디 분석도 이 성질에
  의존한다).

### 비용 측면 트레이드오프도 검토했으나 결정을 바꾸지 않음

옵션 B가 시퀀스를 더 줄이지만, `IMPLEMENTATION_NOTES.md` §4에서 실측했듯
batch=1의 짧은 시퀀스 구간에서 llama-7b forward는 연산량보다 **GPU 메모리
대역폭(가중치 로딩)에 지배**되는 구간이라, 토큰 수를 k개에서 1개로 더 줄여도
얻는 latency 이득은 애초에 크지 않다(all-patch 16개 vs patch-selection 8개
차이도 상한 ~6ms 수준). 즉 옵션 B로 얻는 비용 이득은 작은데 잃는 정보(위 세
가지)는 명확하므로, 옵션 A를 유지하는 것이 합리적이다.

## 4. 오프라인 캐시 방식에서 실시간(on-the-fly) ViT로 전환한 이유

### 문제

원래 `baseline` 방식은 모든 프레임의 CLS 토큰 feature를 **사전에 한 번
추출해 디스크에 캐싱**해 두고(`cfg.dataset_image_features`), 학습/추론 때는
단순히 그 캐시를 읽기만 한다 — ViT를 반복 실행하지 않아 빠르다. 문제는 이
캐싱이 "프레임당 고정된 feature 1개"라는 전제에서만 성립한다는 것이다.

§2~§3에서 정한 `patch-selection` 모드는 **어떤 패치가 선택될지가 샘플마다
(과거 궤적에 따라) 달라진다**. 16개 그리드에서 나올 수 있는 부분집합은
`2^16 = 65536`가지이고, 여기에 top-k 값이나 threshold 값을 바꾸는 경우까지
고려하면 사실상 조합이 무한히 늘어난다. 이 모든 조합에 대한 ViT feature를
미리 계산해 캐싱해 두는 것은 저장 공간과 사전 계산 비용 양면에서 비현실적이다
— 캐싱이 성립하려면 애초에 "무엇을 캐싱할지"가 추론 이전에 고정되어 있어야
하는데, patch selection은 그 전제 자체를 깬다.

### 채택한 해법

`all-patch`/`patch-selection` 모드에서는 frozen ViT(`vit_b_16`)를 Pipeline에
직접 들고 있다가(`Pipeline.__init__`, `models/pipeline.py:105-114`), 추론 시점에
필요한 패치(all-patch는 16개 전부, patch-selection은 선택된 k개)만 그때그때
crop해서 ViT에 통과시키는 실시간 방식으로 전환했다(`_vit_feature_fn()`,
`vit_features_for_patches()`, `models/pipeline.py:318-345`). ViT 자체는 학습되지
않는 frozen feature extractor이므로(`requires_grad_(False)`,
`models/pipeline.py:113-114`), 매번 다시 계산해도 gradient 계산 비용은 없고
forward 연산 비용만 추가된다.

### 당시 고려했던 대안

- **가능한 선택 조합을 미리 열거해 부분 캐싱**: top-k를 고정값(예: k=8)으로만
  운용한다면 조합 수를 줄일 여지가 있었지만, `patch_threshold` 옵션으로 가변
  개수 선택을 지원해야 한다는 요구사항과 애초에 상충한다. 또한 top-k를 고정해도
  `C(16,8)=12870`가지 조합은 여전히 실용적 캐싱 범위를 벗어난다. 기각.
- **패치별로 개별 캐싱 후 필요한 것만 골라 조합**: "16개 패치 각각의 feature를
  프레임당 한 번씩만 캐싱해 두고, 선택 시 그중 몇 개를 골라 쓴다"는 방식은
  이론적으로는 가능하다(패치 자체는 궤적과 무관하게 고정이므로). 그러나 이는
  결국 all-patch와 동일한 사전 계산 비용(모든 프레임의 16개 패치를 전부 ViT에
  통과)을 지불하면서 캐시 관리 복잡도만 추가하는 셈이라, 온라인으로 선택된
  것만 계산하는 현재 방식 대비 이득이 없다(오히려 저장 공간 비용은 16배 더
  든다). 기각.
- **결론**: patch-selection의 핵심 가치(샘플마다 다른 패치 부분집합)를 유지하려면
  ViT 호출을 추론 시점으로 옮기는 것이 유일하게 일관된 방법이었다. 이 전환의
  실제 비용(이미지 디코딩/크롭 오버헤드)은 `IMPLEMENTATION_NOTES.md` §5에서
  별도로 측정했으며, crop 연산 자체는 무시할 수준(0.05ms)이고 병목은 이미지
  디코딩(4.39ms/프레임, 프레임 단위로 캐싱되어 있어 같은 프레임 재방문 시는
  재사용됨)이라는 것도 확인했다.

## 5. 네 가지 결정의 인과 사슬 요약

```
[1] CLS 토큰 1개는 프레임의 공간 정보를 이미 버린 표현
        |  (해결: ViT가 내부적으로 갖고 있는 패치 단위 표현을 꺼내 쓴다)
        v
[all-patch] 16개 패치를 전부 독립 토큰으로 사용 -> 공간 정보는 살지만
            시퀀스 길이 증가 + 관련 없는 패치의 노이즈 유입
        |  (해결: 궤적 조건부로 관련성 높은 패치만 선별)
        v
[2] patch-selection 도입 -> 어떤 패치를 넣을지는 풀었지만,
    선택된 패치를 "어떻게" 넣을지가 남는 질문
        |
        v
[3] 개별 토큰(옵션 A) vs pooling(옵션 B) -> pooling은 [1]에서 이미
    버렸던 공간/개수 정보를 patch 레벨에서 다시 버리는 것과 같아 옵션 A 채택
        |
        v
[4] 하지만 patch-selection은 샘플마다 다른 패치 부분집합을 요구하므로,
    baseline의 "사전 계산 후 캐싱" 전제가 깨짐 -> 실시간 on-the-fly ViT로 전환
```

각 결정은 이전 결정이 남긴 새로운 문제를 푸는 과정에서 나왔다는 점에서, 이
네 가지는 독립적인 실험이 아니라 하나의 일관된 설계 궤적으로 볼 수 있다.
